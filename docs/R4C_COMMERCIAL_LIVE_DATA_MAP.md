This map describes the accepted commercial UI signals and the domain-backed sources available on branch `feat/commercial-command-center-hardening`. It deliberately distinguishes governed live records from presentation-only values. The map is based on the Prisma schema, `CommercialService`, `TurnoverService`, permission seed, and existing workflow tests.

## Status normalization

The aggregate layer preserves domain enums and exposes stable aggregate buckets. `AVAILABLE`, `HELD`, `RESERVED`, and `SOLD` are direct unit states. `DRAFT`, `UNRELEASED`, `BLOCKED`, and `WITHDRAWN` remain separate inventory buckets. Lead statuses remain domain values; `APPOINTMENT` is exposed as `APPOINTMENT` rather than renamed to an unsupported state. `UnitHold.status = ACTIVE` and `Reservation.status = CONFIRMED` are direct governed records.

## Permission and tenant boundaries

Every query includes the authenticated `tenantId`. Portfolio inventory counts are available to users with `commercial:read`. Tenant-wide lead counts and lead-linked exceptions require `commercial:lead:view-all`; users with only `commercial:lead:view-own` receive a scoped lead view rather than cross-team totals. Financial reservation totals remain visible only when the existing commercial read permission is present; no new RBAC model is introduced.

## Explicit limitations

The repository does not model explicit follow-up due dates, a persistent interest status, reservation approval-pending workflow, title-transfer records, or probability-weighted forecasting. These remain unavailable rather than being inferred or fabricated. The first increment uses derived exceptions computed on request and does not add a migration or persistent exception table.
